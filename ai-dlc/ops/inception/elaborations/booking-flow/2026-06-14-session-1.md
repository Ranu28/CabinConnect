## Discussion Notes

### Key Decisions

| Decision | Reasoning |
|---|---|
| Hold has its own `holds` table (not `bookings`) | A Hold is uncommitted and temporary; mixing it with Bookings pollutes the booking lifecycle and complicates the availability query. Separate table keeps concerns clean. |
| Hold statuses: `Active` / `Consumed` / `Cancelled` | `Active` = within window; `Consumed` = used to create a Booking; `Cancelled` = expired or abandoned. Consumed Holds are kept for audit. |
| Hold consumption and Booking creation in one DB transaction | Prevents EC-012: if Booking creation fails mid-flight, the Hold rolls back to Active rather than being stranded as Consumed with no Booking. |
| One Active Hold per Guest at a time | Prevents Guests holding multiple cabins simultaneously. Placing a new Hold auto-cancels the previous one. This is enforced at the API layer before inserting the new Hold. |
| Total price calculated at Booking confirmation, not at Hold creation | EC-006: price is frozen at confirmation. The Hold stores the dates; price is computed fresh at `POST /api/bookings` using `NightlyRateCalculator`. Client is never trusted for price. |
| Availability query (CSA-002) updated as part of BKF-001 | The search endpoint must exclude cabins with Active Holds from the moment Hold creation exists; shipping BKF-001 without this update would allow double-Hold on the same cabin. |
| Hold expiry job uses a `WHERE expires_at < now() AND status = 'Active'` query | Simple and safe; idempotent. Running more frequently than 5 min is harmless. |
| Booking Confirmation page is a separate unit from Checkout | Different responsibilities: Checkout drives the transaction; Confirmation is a read-only success view. Separating them keeps the Checkout page focused on error handling. |
| Host Booking Management is Low priority | Hosts cannot reject bookings in this intent; the management view is useful but not blocking the core booking flow. |
| `payment_intent_id` stored on Booking, nullable for now | Stripe integration is out of scope; column is included so the schema does not need a breaking change when Stripe is introduced. |
