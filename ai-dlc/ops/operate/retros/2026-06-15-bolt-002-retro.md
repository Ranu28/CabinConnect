# Retrospective: BOLT-002 — Booking Flow

**Bolt:** [BOLT-002](../../build/bolts/2026-06-14-bolt-002-booking-flow.md)
**Date:** 2026-06-15
**Participants:** RP
**Facilitator:** RP

## What Went Well

- **All 9 units completed, including the stretch (BKF-009).** The bolt plan designated BKF-009 as "drop if BKF-001–BKF-008 aren't solid" — all 8 core units were solid so the stretch landed too.
- **EC-012 atomic transaction implemented correctly first time.** `SELECT FOR UPDATE OF h` (hold row only, not cabin) + `INSERT booking` + `UPDATE hold=Consumed` in a single transaction, with rollback on any exception. The unit spec was precise enough that no revision loop was needed.
- **EC-007 info-leak prevention was well-specified and consistently applied.** Cancel Booking returns 404 for both "not found" and "not owned" — the unit notes made the reasoning explicit and it was implemented without prompting.
- **`IServiceScopeFactory` pattern applied correctly for `HoldExpiryService`.** Background services are singletons; resolving scoped services (`IHoldRepository`) per-tick via a scope is the correct pattern. Once the test failure revealed the problem, the fix was clean and architecturally sound.
- **Auth wired end-to-end in one pass.** Supabase JWT Bearer (backend) + `apiFetch` with Bearer injection + `useAuth` + `RequireAuth` guard (frontend) were all built together, so no unit was left with a partial auth story.
- **Frontend pages used sessionStorage for refresh-safe countdown (BKF-006 AC-2).** Storing `hold:{holdId}` in sessionStorage means the Checkout page countdown survives a browser refresh — a subtle requirement that was addressed without needing a `GET /api/holds/{id}` endpoint.
- **Unit files pre-written with ACs made "continue" prompts efficient.** A single "continue with rest of the bolts" instruction was enough to drive BKF-003 through BKF-009 because the unit files contained all four quality gate components.
- **75 tests passing at bolt close** (24 domain + 27 API + 24 frontend), no regressions against BOLT-001 output.

## What Didn't Go Well

- **`HoldExpiryService` initially injected `NpgsqlDataSource` directly.** This caused all 23 API tests to fail immediately — the `AddSingleton` factory lambda throws when the connection string is null (by design for production), but that throw now fired during every test startup. Required recognising the `IServiceScopeFactory` pattern and refactoring before any other work could proceed.
- **`Microsoft.Extensions.Hosting.Abstractions` was missing from the Infrastructure project.** `BackgroundService` and `IConfiguration` aren't in the shared framework for a class library; a NuGet package was needed. This was a minor friction but a build failure that could have been anticipated.
- **BKF-005 AC-3 price accuracy is an approximation.** The Cabin Detail Page shows `nights × baseRate` as the estimated price, ignoring seasonal rates. The unit spec said "fetch from search API OR compute client-side" — client-side was chosen for simplicity but doesn't reflect seasonal pricing. A Guest may see a different total on the Checkout Page than on the Detail Page.
- **My Bookings page (BKF-008) loads only the first page.** The pagination API contract was implemented on the backend (`page`/`pageSize` params, `totalCount` in response) but no pagination UI was added to the frontend list. A Guest with many bookings has no way to load more.
- **Running API process locked DLLs during BKF-009 test run.** A previously-started `dotnet run` held the `.dll` files; `dotnet test` failed to copy the newly-built assemblies. Required `Stop-Process` to unblock. This is an environment issue, not a process issue, but it broke the flow.
- **Auth was a carryover stub from BOLT-001.** JWT Bearer configuration was never wired in BOLT-001 — all `[Authorize]` endpoints would have returned 401 for real Supabase tokens in production. It was caught at the start of this session, but ideally auth would have been part of BKF-001's definition of done.
- **EC-011 and EC-012 integration tests were not written.** The bolt's Definition of Done explicitly required integration tests for the atomic Hold→Booking transaction and the auto-cancel of the prior Hold. These still require a real PostgreSQL instance (Testcontainers or a test DB) and were not completed.
- **Frontend unit tests for new pages were not added.** BKF-005 through BKF-009 pages are not covered by Vitest. Testing them requires mocking `apiFetch` and the Supabase client — deferred but not ideal.

## AI-Specific Observations

### Prompts that worked as expected

- **"start BKF-00X" with a fully pre-written unit file** — same pattern as BOLT-001; complete ACs in the unit file meant every unit produced usable output on the first generation. No revision loops for backend units.
- **Batching related frontend units (BKF-005–BKF-008)** — generating the auth system, API client, and all four pages in one pass was efficient. The shared patterns (`RequireAuth`, `apiFetch`, navigation state) were applied consistently because they were established once and reused.
- **EC-007 note in unit spec ("404 not 403, info-leak prevention")** — explicit reasoning in the unit file prevented the common mistake of returning 403 for unowned resources. The AI followed the reasoning, not just the rule.

### Prompts that needed revision before output was usable

- **`HoldExpiryService` initial implementation** — the first version injected `NpgsqlDataSource` directly. The output was structurally correct but architecturally wrong for a hosted service in the test environment. The test failure was the signal; the fix required understanding the singleton/scoped boundary. The unit file did not specify the DI pattern explicitly — this is worth adding to the unit template or infrastructure guidelines.

### Quality gate failures caught

- No gate failures during build — all four components were present in every prompt before code was generated.

### Cases where AI output was accepted without enough review

- **BKF-005 price estimate accepted without flagging the seasonal rate gap.** The `nights × baseRate` computation was a known simplification but was not explicitly marked as an approximation in the UI ("estimated"). A Guest who sees $300 on the Detail Page and $350 on the Checkout Page (due to a seasonal rate) would be confused. This should have been caught in review.
- **`HoldExpiryService` DI pattern was not reviewed before running tests.** The `BackgroundService` → scoped dependency boundary is a well-known .NET pitfall; a reviewer familiar with the pattern would have caught it before the test run.
