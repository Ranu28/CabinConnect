# Retrospective: UIR — User Identity & Roles

**Bolt:** *(informal — no bolt plan; UIR-001–003 built as a prerequisite patch after BOLT-002)*
**Date:** 2026-06-15
**Participants:** RP
**Facilitator:** RP

---

## What Went Well

- **All three units landed in one session.** DB migration, backend API, and all three frontend pieces (registration, nav bar, profile hook) were built, tested, and passing without a revision loop.
- **Role enforcement on the Host endpoint was added cleanly.** `HostController` now reads `user_profiles.role` from the DB and returns 403 for non-host callers. The test fixture was updated in the same pass — no regressions.
- **Registration two-step flow handled gracefully.** `supabase.auth.signUp()` → `POST /api/me/profile` is a two-step sequence; the email-confirmation-pending case (no session returned) is handled with an informational message rather than a crash.
- **`CREATE POLICY IF NOT EXISTS` syntax error caught quickly.** Supabase runs PostgreSQL < 17; the migration failed immediately in the SQL editor and was fixed to the `DROP POLICY IF EXISTS` + `CREATE POLICY` pattern. Same fix applied retroactively to migration 003.
- **51/51 backend tests and 24/24 frontend tests remained green** throughout.

## What Didn't Go Well

- **UIR was never formally planned as a bolt.** The intent file, elaboration session, unit files, and bolt plan were all skipped. The work was triggered by observing a gap ("frontend goes straight to cabin search, no auth flow visible") rather than from a planned unit. Units are tracked in the backlog post-hoc.
- **No acceptance criteria were written before coding.** The quality gate was satisfied verbally in the conversation rather than from pre-written unit files. This is the same pattern that caused the BOLT-001 auth stub — work done outside the AI-DLC flow lacks a testable spec before coding starts.
- **Admin role mechanics are undefined.** The user confirmed Admin is needed "for Host promotion" but there is no Admin UI, no promotion endpoint, and no way to grant the admin role except a direct DB update. This is an intentional deferral but was not captured as a future unit.
- **Host nav shows only "Host Bookings" — Hosts cannot view their own bookings as a Guest would.** The nav bar logic (`guest/admin → My Bookings`, `host/admin → Host Bookings`) means a user who registered as a Host has no way to view bookings they made as a booker. Product decision not made; deferred.

## AI-Specific Observations

### Prompts that worked as expected

- **Migration error → immediate fix** — `CREATE POLICY IF NOT EXISTS` syntax error in Supabase was surfaced visually by the user; the fix (drop-and-recreate pattern) was applied to both migration 003 and 004 in one pass.
- **Test fixture update alongside controller change** — When `HostController` gained a new dependency (`IUserProfileRepository`), the failing tests were diagnosed immediately by reading the `FakeAuthHandler.GuestId` constant and updating `BuildClient` to stub the profile repo. No second round of failures.

### Prompts that needed revision before output was usable

- None — the output was usable on the first pass for all three units.

### Quality gate failures caught

- No formal gate was run — the request did not go through the four-component quality gate (Context / Constraints / Acceptance Criteria / Output Format) because UIR was treated as an unplanned prerequisite patch rather than a unit. This is itself the process gap.

### Cases where AI output was accepted without enough review

- **Nav bar role logic for Hosts** — the decision to hide "My Bookings" from Hosts was embedded in the implementation without a product discussion. A Host who has booked a cabin has no UI to see it. This should have been a design question before coding.
