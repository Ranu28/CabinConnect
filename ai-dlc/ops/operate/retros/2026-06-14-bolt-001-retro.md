## What Went Well

- **Parallel track structure held.** CSA-003 and CSA-004 were built and tested against mocks while the backend track ran — no blocking between tracks.
- **All five high-priority units completed within the planned window** (2026-06-12 → 2026-06-14, inside the 2026-06-19 deadline). CSA-006 was pre-declared droppable and correctly left out.
- **Prompt quality gate prevented underspecified requests from reaching code generation.** Every prompt log shows all four components present before output was produced.
- **CSA-001 rate resolution logic was validated before CSA-002 built on it** — the "most specific wins, tie → higher rate" risk item from the bolt plan was handled without a regression at integration time.
- **EC-003 (UTC date-only) held end to end** — no timezone leak across the date picker, API parsing, and SQL comparisons.
- **Short, sharp unit prompts worked.** "start CSA-002" with a fully specified unit file produced 16 source files and 25 passing tests on the first run.

## What Didn't Go Well

- **Npgsql `IN @Param` syntax error hit at runtime, not at test time.** Dapper's `IN @CabinIds` expansion is SQL Server–style and silently produces invalid SQL under Npgsql. The API returned a 500 before any search result was seen. The fix (`= ANY(@Param)`) is straightforward but wasn't caught by unit or integration tests because they mock the repository.
- **Integration tests don't exercise the real SQL path.** The `CabinSearchRepository` has no test that runs against an actual PostgreSQL instance, so database-level syntax errors are invisible until `dotnet run`.
- **The bolt plan listed "validate AC-15 performance against 10k-cabin seed" but this was not completed.** The seed data exists but the performance acceptance criterion was not verified.

## AI-Specific Observations

### Prompts that worked as expected

- **"start \<unit-id\>" with a fully written unit file** — providing complete acceptance criteria, constraints, and output format in the unit file meant the prompt itself could be minimal. Output was on-target every time with no revision loop for CSA-001 through CSA-005.
- **Constraint-first framing in unit files** — listing what must NOT be done (`.Result`/`.Wait()`, raw SQL, `any` without comment) before what must be done steered the AI away from common mistakes without needing correction.

### Prompts that needed revision before output was usable

- None for code generation this bolt — all five units produced usable output on the first prompt. Minor wording clarifications were needed during elaboration, not during build.

### Quality gate failures caught

- No gate failures during build. Gate was applied correctly at the start of each unit; no code was generated from an incomplete prompt.

### Cases where AI output was accepted without enough review

- **`CabinSearchRepository` SQL was not reviewed for Npgsql compatibility before merging.** The repository code looked correct to a SQL Server reader and passed all mocked tests — the Npgsql-specific `= ANY()` requirement was not on the reviewer's checklist. This is the direct cause of the runtime 500.
